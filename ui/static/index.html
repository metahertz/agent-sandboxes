SSH keys

Claude gets an ssh-agent holding only these keys — never the key files. Changes apply immediately, even to a running session. Git uses them via GIT_SSH_COMMAND; SSH goes through the network allowlist below.

API tokens

Claude sees a placeholder in the environment variable; nono's proxy swaps in the real token only on requests to that service. Restart Claude to apply.

Apple signing

Identities Claude may have things signed with, through the aio-builds MCP server (so Apple builds must be on too). Claude never gets the key or the .p12. Applies at once.

Network

Outbound traffic from Claude and everything it runs passes through nono's filtering proxy. An allowed host is reachable on any port, unless you list it with ports: then only those (port changes apply at once, the rest when Claude restarts). Programs that ignore HTTPS_PROXY (database clients, for example) can't connect; SSH and git are set up to use it. Restart Claude to apply.

nono can't limit which address a server binds, so one on 0.0.0.0 is reachable from your network unless the host's firewall blocks it. Ports this app uses (6101–6199, 7100–7199, 8101–8199, 9101–9199, 3128, 4318) and other workspaces' listen ports are refused.

Container network (the sandbox's browser, VS Code and terminal)

“Same as Claude” puts the container on a network with no route out; its browser and shell tools use the proxy, and the rest (DNS, raw TCP) can't connect. Allowlist changes apply to the container at once; switching this, or changing its tokens, recreates the container (its browser session restarts). VS Code extensions need open-vsx.org allowed.

This VM has no network interface: everything in it (Claude, apt, Docker, git over ssh) goes through its proxy on the host, with this allowlist, which applies at once. claude.ai and downloads.claude.ai are always allowed, for installing Claude Code in the VM. Token changes apply when the VM restarts.

Apple builds

Each job is a commit of the project's git repository, pushed by this host to the build host and run by a Mac worker in a fresh macOS VM that's deleted afterwards. The agent gets MCP tools only, never a key or a connection to the build host or the Mac. Set up the build host and workers under Build workers. Restart the agent to apply.

Browser container

The same container as a sandbox workspace's, inside the VM: its network is the VM's (this allowlist, through the proxy), and the Browser, VS Code, Terminal and Files tabs reach it over vsock. Its image (about 13 GB) is copied from this host into the VM's disk on the first start, which takes a few minutes; the VM's memory default goes up to the container's memory plus 3G (5G) and its disk to 48G (sparse). Restart the VM to apply.

Resource limits

Applied to Claude's whole process tree via cgroups (CPUs as a CPU quota: 2 = two cores' worth). Leave empty for no limit. Restart Claude to apply.

The VM's size. Empty means the default: 2G of memory (with the browser container, its memory plus 3G), 2 vCPUs, and a 16G disk (48G with the browser container). The disk is sparse, so it only takes the space the VM writes, and it can grow but never shrink. Restart the VM (Stop, then Start) to apply.

Browser container

The AIO container's memory (Chromium's shared memory is the same size, inside it) and CPUs. Empty means 2G and 2 CPUs. Saving a change recreates a running container, so its browser session restarts.Only used with the browser container ticked; at most the VM's vCPUs, and the VM needs 1G more memory than the container. Restart the VM to apply.

Notes for Claude

A marked block at the end of the file, refreshed whenever Claude starts and removed when you untick this; the rest of the file is left alone. It's part of the project, so it shows up in git. Whether or not this is on, Claude is told at startup how to call this workspace's API tokens.

Remote terminal (SSH)

Keys added here log in to this workspace only: its Claude session, or a shell and file transfer inside the same nono sandbox as Claude. They apply immediately. Use a key that isn't already allowed to log in to this host.

API tokens

            

          

            

              
              
            

            

              
              
              
              
              
              
              
              
Not just bearer tokens: anything the API takes in a header (e.g. X-Client-Id with format {}), a query parameter (?client_id=), the URL path, or Basic auth (store client_id:client_secret). The agent only gets a placeholder, which the proxy swaps there and nowhere else: not in a request body, a file or a browser address.

              
For an http:// API, Claude calls $POOL_<NAME>_BASE_URL (e.g. $POOL_GRAFANA_RO_BASE_URL/api/search) instead of the real URL; the token is added on the way and travels unencrypted from this host to the API. HTTPS APIs work at their own URL too.

Apple signing

            

          
A signing certificate with its private key (.p12) and its provisioning profiles, for workspaces with Apple builds. They stay on this host: a key is used for signing, which no proxy can do on the agent's behalf, so the agent asks the aio-builds MCP server instead. export_build signs an archive on a Mac with Xcode (sealed for that one job, deleted with its VM) and can upload it to TestFlight with an App Store Connect key; sign_ipa re-signs on this host with rcodesign.

          

            

              
              
              
            

            
            
Export the certificate from Keychain Access (My Certificates → the certificate → Export, as .p12); download profiles from developer.apple.com → Certificates, IDs & Profiles → Profiles.

Build workers

        
Machines outside this host that build workspaces' code for platforms it can't: Apple (Xcode) on Macs, for now.

      


      

      

        

          
Apple builds
…

          
Xcode builds for workspaces with Apple builds ticked. There are three parts: this host queues each job (a commit, tagged build/<id>); the build host, a plain git queue over ssh between this host and the Macs, keeps the jobs, logs and results (usually this machine, set up by bin/install-buildhost); and Mac workers connect out to it, take jobs and run each in a throwaway Tart VM (set up by buildhost/install-worker).

          
Nothing here can reach a Mac: Macs only connect out, so they can sleep or sit behind NAT and pick jobs up when back, and several can share the queue. Put the build host on another Linux host only if the Macs can't reach this machine's ssh port.

          

            

              
              
            

            

              

          

          
This host's key, for the build host's aio-buildd ui-key (the installer adds it for a build host on this machine):

           
          

            Set up a build host and Mac workers
            
1. The build host (the queue)

            
On this machine (the usual case), in the agent-sandboxes folder; it needs an ssh server. It creates the aiogit user, gives this host's key the ui role and fills in the form above:

            
bin/install-buildhost && sudo systemctl restart agent-sandboxes-ui 

            
Or on another Linux host with git and an ssh server: download the installer there, run it with this host's key, then set its address above as aiogit@<that host> and Test connection.

            
⬇ aio-buildhost.tar.gz

            
 

            
2. A Mac worker

            
On a Mac with Apple silicon, Tart and Python 3.9+ (xcode-select --install), logged in as the user whose VMs it should use. It only connects out, to the build host's ssh port, which must be reachable from the Mac. Download the worker, then run:

            
⬇ aio-build-worker.tar.gz

            
 

            
It installs into ~/.aio-build with a LaunchAgent, and prints the worker's name and key: add them under Mac workers below. Then pull the image once (tart pull ghcr.io/cirruslabs/macos-sequoia-xcode:latest), so the first build doesn't wait for it.

            
3. A workspace

            
Tick Apple builds on its Access tab and restart its agent.

Backup to a NAS

          
Packs what you choose below into one tarball and copies it to an SMB (CIFS) share with smbclient, so nothing is mounted. Settings, including the password, are kept in secrets/backup.json, which Claude can't read.

          

          

            
            
          

          

            
            
          

          

            
            
          

        


        

          
What to back up

          

            
            
            
            
          

          
The tarball isn't encrypted, and with the last two ticked it holds private SSH keys, API tokens and Claude's login. Keep the share private to you.

        


        

          
Schedule and retention

          

            
            
            
          

          

            
            
            
          

          
Times are this host's local time. A run missed while the host was off starts when the UI is back. After each backup, this host's backups older than the limit are deleted from the share, apart from the newest. Backups from other hosts in the same folder are left alone.

        


        

          
          
          
          

        

      


      

        

          
Backups on the NAS

            

              

          

          

          
To restore, copy a tarball back, look inside with tar -tf FILE, then extract to a scratch folder (tar -xf FILE -C DIR) or in place (-C /; stop the UI and Claude first). Paths are stored relative to /, and BACKUP-MANIFEST.json lists what's inside.
